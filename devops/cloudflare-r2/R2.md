# Cloudflare R2

## ¿Qué es?

Cloudflare R2 es un servicio de **almacenamiento de objetos** (ficheros con su metadato, guardados en *buckets* y accesibles por HTTP) que habla el mismo protocolo que Amazon S3 pero **no cobra por el tráfico de salida**.

## ¿Por qué existe?

Una aplicación que acepta subidas de usuarios —fotos de producto, facturas en PDF, avatares— no debería guardarlas en el disco del servidor: se llena, se pierde con el servidor y no escala a varias instancias. La solución estándar es un almacén de objetos externo, y durante años eso significó Amazon S3.

S3 funciona muy bien, pero cobra cada gigabyte que **sale** hacia internet. Para una tienda online que sirve miles de imágenes al día, esa factura de *egress* acaba pesando más que el propio almacenamiento, y además ata al proveedor, porque mover los datos fuera también cuesta.

R2 nace para quitar esa penalización: mismo modelo de uso, compatible con las librerías y herramientas de S3, y sin cargo por descarga.

> Si ya conoces S3, piensa en R2 como "S3 con otra URL y otra factura": el código cliente casi no cambia, lo que cambia es el endpoint y las credenciales.

## ¿Cuándo y para qué se usa?

- **Imágenes y descargas servidas al público**: catálogo de una tienda, adjuntos de un blog, instaladores. Es donde el egress gratuito más se nota.
- **Subidas de usuarios**: el navegador sube el fichero directamente al bucket, sin pasar por la API.
- **Copias de seguridad y logs**: volcados de base de datos, exportaciones periódicas.
- **Sustituir a S3** en una aplicación existente, cambiando solo configuración.

No es un sistema de ficheros ni una base de datos: no hay carpetas reales, un fichero no se edita a medias (se reemplaza entero) y no se consulta por contenido.

## Conceptos básicos

- **Bucket**: contenedor con nombre. Suele haber uno por "tipo de cosa" (`tienda-media`, `tienda-backups`). Los permisos y las reglas se aplican por bucket.
- **Objeto**: un fichero más su metadato (`Content-Type`, `Cache-Control`, pares clave-valor propios). Hasta 5 TiB cada uno.
- **Clave** (*key*): el nombre completo del objeto dentro del bucket, por ejemplo `products/42/front.jpg`. Las barras son solo caracteres del nombre; las "carpetas" de los paneles salen de agrupar por prefijo.
- **ID de cuenta**: identificador de tu cuenta de Cloudflare. Forma parte del endpoint S3.
- **Endpoint S3**: `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`. La región es siempre `auto` (R2 acepta también vacío o `us-east-1` como alias).
- **Clase de almacenamiento**: *Standard* (por defecto) o *Infrequent Access* (más barata de guardar, con cargo por lectura).

## Primeros pasos: bucket, credenciales y una subida

### 1. Crear el bucket

Desde el panel (**R2 Object Storage → Create bucket**) o con `wrangler`, la CLI de Cloudflare:

```bash
npx wrangler r2 bucket create tienda-media
```

### 2. Crear un token de API

En **R2 → Manage API tokens** se crea un token que genera dos valores: el **Access Key ID** y el **Secret Access Key**. Son las credenciales que usará cualquier cliente S3. El secreto se muestra una sola vez.

El token tiene un nivel de permiso:

| Permiso | Qué permite |
|---|---|
| Admin Read & Write | Crear y borrar buckets, cambiar su configuración y leer/escribir objetos. |
| Admin Read only | Listar buckets, ver su configuración y leer objetos. |
| Object Read & Write | Leer, escribir y listar objetos, **limitado a los buckets que elijas**. |
| Object Read only | Leer y listar objetos de los buckets elegidos. |

Para una aplicación, lo correcto es **Object Read & Write** restringido al bucket que usa.

### 3. Subir y listar con cualquier herramienta S3

Con la AWS CLI, indicando el endpoint de R2:

```bash
export AWS_ACCESS_KEY_ID=<ACCESS_KEY_ID>
export AWS_SECRET_ACCESS_KEY=<SECRET_ACCESS_KEY>
export AWS_DEFAULT_REGION=auto
ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com

aws s3 cp ./front.jpg s3://tienda-media/products/42/front.jpg --endpoint-url $ENDPOINT
aws s3 ls s3://tienda-media/products/ --endpoint-url $ENDPOINT
```

La primera línea sube el fichero; la segunda lista el prefijo `products/`:

```
                           PRE 42/
```

Cualquier otra herramienta compatible con S3 (rclone, Cyberduck, los SDK) funciona igual: endpoint, región `auto` y las dos claves.

## Usarlo desde código

### .NET

Se usa el SDK oficial de AWS (`AWSSDK.S3`) apuntando al endpoint de R2:

```csharp
var credentials = new BasicAWSCredentials(accessKey, secretKey);
var s3 = new AmazonS3Client(credentials, new AmazonS3Config
{
    ServiceURL = "https://<ACCOUNT_ID>.r2.cloudflarestorage.com"
});

await s3.PutObjectAsync(new PutObjectRequest
{
    BucketName = "tienda-media",
    Key = "products/42/front.jpg",
    InputStream = stream,
    ContentType = "image/jpeg",
    DisablePayloadSigning = true,
    DisableDefaultChecksumValidation = true
});
```

Las dos últimas propiedades son obligatorias en las subidas: R2 no soporta el *Streaming SigV4* que el SDK usa por defecto. Sin ellas la subida falla.

### JavaScript / TypeScript

```ts
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";

const s3 = new S3Client({
  region: "auto",
  endpoint: `https://${ACCOUNT_ID}.r2.cloudflarestorage.com`,
  credentials: { accessKeyId: ACCESS_KEY_ID, secretAccessKey: SECRET_ACCESS_KEY },
});

await s3.send(new PutObjectCommand({
  Bucket: "tienda-media",
  Key: "products/42/front.jpg",
  Body: fileBuffer,
  ContentType: "image/jpeg",
}));
```

Lo que se ve en cualquier tutorial de S3 sobre `GetObject`, `DeleteObject`, `ListObjectsV2` o subidas multiparte vale tal cual.

## Entregar los ficheros: cuatro formas de dar acceso

Un bucket nuevo es **privado**. Hay cuatro maneras de que alguien descargue un objeto, y elegir bien es la decisión de diseño más importante con R2.

| Forma | Cuándo usarla | Control de acceso |
|---|---|---|
| **Pasando por tu API** | Ficheros sensibles, con reglas de negocio. | Total, pero el tráfico pasa por tu servidor. |
| **URL prefirmada** | Descarga o subida puntual de un fichero privado. | Caduca (de 1 segundo a 7 días). |
| **Dominio personalizado** | Contenido público de producción (imágenes del catálogo). | Público, con caché y WAF de Cloudflare. |
| **Subdominio `r2.dev`** | Solo pruebas. | Público, con límite de peticiones y sin caché. |

### URLs prefirmadas

Una URL prefirmada lleva en la propia dirección una firma que autoriza **una operación sobre un objeto concreto** durante un tiempo limitado. La API la genera con sus credenciales y se la entrega al navegador; el navegador habla directamente con R2.

```ts
import { GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const url = await getSignedUrl(
  s3,
  new GetObjectCommand({ Bucket: "tienda-media", Key: "invoices/2026/0042.pdf" }),
  { expiresIn: 600 } // 10 minutos
);
```

`url` es una dirección del estilo `https://<ACCOUNT_ID>.r2.cloudflarestorage.com/tienda-media/invoices/...?X-Amz-Signature=...`. Quien la tenga puede descargar esa factura durante diez minutos, y nada más.

Para **subidas**, el patrón es el mismo con `PutObjectCommand`: la API genera una URL de subida, el navegador hace `PUT` del fichero directamente al bucket y el servidor nunca carga con los bytes.

Se admiten `GET`, `HEAD`, `PUT` y `DELETE`. Dos limitaciones: **no funcionan con dominios personalizados** (solo con el endpoint S3) y no se admiten subidas con formulario `POST`.

### Dominio personalizado

Para servir contenido público en producción, el bucket se conecta a un dominio gestionado en Cloudflare (por ejemplo `cdn.ejemplo.com`) desde **Bucket → Settings → Custom Domains**. Eso da:

- Caché de Cloudflare delante del bucket (menos peticiones facturables y más velocidad).
- Reglas WAF, gestión de bots y, si hace falta, Zero Trust Access para restringirlo a un equipo.
- Control del TLS.

Con eso, `https://cdn.ejemplo.com/products/42/front.jpg` sirve la imagen desde caché. El subdominio `r2.dev` (se activa en *Settings → Public Development URL*) sirve para probar rápido, pero tiene límite de peticiones y no cachea: no es para producción.

### CORS

Si el navegador hace `fetch` o `PUT` desde `https://tienda.ejemplo.com` hacia el bucket (subidas con URL prefirmada, por ejemplo), hace falta una política CORS que lo permita. Sin ella el navegador bloquea la petición aunque la firma sea correcta. En el panel, **Bucket → Settings → CORS Policy**:

```json
[
  {
    "AllowedOrigins": ["https://tienda.ejemplo.com"],
    "AllowedMethods": ["GET", "PUT"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

Permite a ese origen leer y subir, enviar `Content-Type` y leer el `ETag` de la respuesta. Si se aplica con `wrangler` (`npx wrangler r2 bucket cors set tienda-media --file cors.json`), el fichero usa otro formato (`{"rules": [{"allowed": {"origins": [...], "methods": [...]}}]}`); no es el mismo JSON que el del panel.

## Costes y límites

| | Standard | Infrequent Access |
|---|---|---|
| Almacenamiento | 0,015 $/GB·mes | 0,01 $/GB·mes |
| Operaciones de Clase A (escritura, listado) | 4,50 $ por millón | 9,00 $ por millón |
| Operaciones de Clase B (lectura) | 0,36 $ por millón | 0,90 $ por millón |
| Recuperación de datos | — | 0,01 $/GB |
| Salida a internet (*egress*) | Gratis | Gratis |
| Duración mínima | — | 30 días |

Hay un plan gratuito mensual en Standard: 10 GB de almacenamiento, 1 millón de operaciones de Clase A y 10 millones de Clase B. El borrado no se cobra. Cifras de la página oficial de precios consultada el 2026-10-01; conviene recomprobarlas antes de presupuestar.

Límites que conviene conocer:

- Objeto: 5 TiB como máximo. Una subida simple llega a 5 GiB; por encima hay que usar **subida multiparte** (hasta 10 000 partes).
- Clave: 1024 bytes. Metadato: 8192 bytes.
- **Escrituras concurrentes sobre la misma clave: una por segundo.** Si varios procesos reescriben el mismo objeto sin parar, recibirán errores de límite de tasa.
- Buckets por cuenta y objetos por bucket: prácticamente ilimitados.

## Ciclo de vida: borrar y archivar solo

Las **reglas de ciclo de vida** se configuran por bucket (panel, `wrangler r2 bucket lifecycle` o API S3) y automatizan tres cosas:

- Borrar objetos pasados N días o en una fecha concreta (útil para logs y copias antiguas).
- Pasar objetos de Standard a Infrequent Access tras N días.
- Abortar subidas multiparte incompletas (R2 ya las aborta a los siete días por defecto).

El borrado no es instantáneo: los objetos suelen desaparecer en las 24 horas siguientes a su caducidad. El paso a Infrequent Access es **de ida**: una regla no devuelve el objeto a Standard, y cuenta como operación de Clase A.

## Compatibilidad con S3: lo que no hay

La API S3 de R2 cubre lo cotidiano (objetos, multiparte, copia, CORS, ciclo de vida, cifrado con clave del cliente SSE-C). No implementa, entre otras cosas, **versionado**, ACL, etiquetas de objeto (*tagging*), replicación, bloqueo de objetos (*object lock*) ni cifrado con KMS. Un código que dependa de alguna de ellas no migra sin cambios.

## Errores frecuentes

| Síntoma | Causa habitual |
|---|---|
| `AccessDenied` / `403` al subir | El token es *Object Read only*, o no incluye ese bucket. |
| Error de firma en .NET al subir | Faltan `DisablePayloadSigning` y `DisableDefaultChecksumValidation`. |
| La URL prefirmada no funciona con `cdn.ejemplo.com` | Las prefirmadas solo valen con el endpoint S3, no con dominios personalizados. |
| El navegador bloquea la subida (error de CORS) | Falta política CORS para ese origen y método. |
| `NoSuchBucket` | ID de cuenta equivocado en el endpoint, o bucket creado en otra jurisdicción (UE, FedRAMP), que tiene su propio endpoint. |
| Errores de límite de tasa al reescribir | Más de una escritura por segundo sobre la misma clave. |

## Buenas prácticas avanzadas

- **Un token por aplicación y por bucket.** Un token *Object Read & Write* acotado a `tienda-media` limita el daño si se filtra: no puede tocar las copias de seguridad ni borrar buckets. Reutilizar un token Admin en todas partes es la fuente de la mayoría de incidentes serios con almacenes de objetos.
- **Sube directamente desde el navegador con URL prefirmada.** Pasar los ficheros por la API consume ancho de banda, memoria y tiempo de petición. La API solo decide quién puede subir y firma; el binario va directo al bucket. Genera la clave en el servidor (por ejemplo con un GUID) para que nadie elija dónde escribe.
- **Pon `Cache-Control` al subir.** Los objetos inmutables (la clave cambia cuando cambia el contenido) admiten `public, max-age=31536000, immutable`. Con dominio personalizado, la caché de Cloudflare absorbe casi todas las lecturas y las operaciones de Clase B bajan casi a cero.
- **Nombra las claves pensando en el prefijo.** Como no hay carpetas, listar y aplicar reglas de ciclo de vida dependen del prefijo: con `backups/db/2026-10-01.sql.gz`, una sola regla borra todo `backups/db/` tras 30 días; con `2026-10-01-db-backup.sql.gz` en la raíz, no.
- **No uses Infrequent Access para lo que se lee a menudo.** El cargo por recuperación, las operaciones al doble de precio y los 30 días mínimos facturados lo encarecen frente a Standard en cuanto el objeto se lee con regularidad. Resérvalo para copias y archivo.
- **Mantén la regla de aborto de subidas multiparte.** Una subida interrumpida deja partes ocupando espacio facturable hasta que se aborta; el valor por defecto de siete días evita ese goteo, así que no lo desactives.
